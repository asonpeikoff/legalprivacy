# Changelog

## Unreleased

- **A phone version: legalPrivacy Noise for Android (first build, sideloaded).** It makes the same kind of noise from the phone itself: bursts of DNS lookups (A, AAAA and HTTPS records over TLS to Quad9, Cloudflare or Google), page visits to popular sites and searches (DuckDuckGo mostly, a little Google), at random gaps around Low (about 30 an hour), Medium (120) or High (400). It only runs on Wi-Fi unless you change that, can be limited to charging, has a daily data limit (50 MB by default), never visits a site that resolves into a US Department of Defense address block, and pauses when the battery is low. Optional **local DNS VPN**: Android's VPN API carries only the phone's DNS lookups to the app (nothing else is routed), which sends them on over TLS to a secure resolver and keeps its noise in step with your real use; it does not hide which sites you connect to, only one VPN can run at a time, and Android's Private DNS setting (when set to a named provider) bypasses it. No Tor and no relay on the phone, and no Virginia list (too big to carry). The APK is built by the new `Android` workflow (`android/`; the core logic has unit tests, 8 passing here) and attached to a release as `legalprivacy-noise-android.apk` when that workflow is run with the release tag. Not yet run on a real phone: the app has only been compiled and tested by the build, so expect first-run rough edges.

## v2.23.0

- **A Clear button for tested proxies** (Tools → Proxies, web and desktop): throws out every tested proxy at once.
- **More onion (Tor) noise.** The onion budget was low (≈40/day, ~1–2 an hour), so Tor often looked idle. Raised to ≈240/day (about 10 an hour on average, with the usual random pacing so it varies a lot) so onion visits are visible; the light/heavy presets rise too.

- **Speed test fixed (was 403 on download and upload).** The request carried no User-Agent, and speed.cloudflare.com answers 403 without one; it now sends a normal browser User-Agent. The speed test uses only a clearnet proxy you set in Settings — never the tested free-proxy pool.
- **Proxy tester tries far more candidates.** It tested only 400 new candidates per run; the cap is now 2,500, and the progress line shows how many were found versus tested (e.g. "testing 120/2500 of 1,900 found"). Free public proxies are mostly dead or slow regardless, so few will pass.

- **The noise no longer skips non-English sites.** The English-only filter (which skipped sites on country domains like `.de`, language sections like `/fr/`, and pages declaring a non-English `<html lang>`, and rested them for a week) is removed, so every language is visited like any other. The "not in English: moved on" activity-log line is gone.

- **Load test (your own target), on the Tools tab.** Generates load from this one computer and graphs it live (requests/s, ok vs failed, bytes, latency p50/p90/p99). L7 sends real HTTP requests (GET/HEAD/POST); L4 opens real TCP connections. It never spoofs addresses or forges packets, there is no way to drive other machines from it, and it refuses government/Virginia address ranges. It will not start until you confirm you own the target or are authorised to test it, and it is capped (2000/s, 256 concurrent, 600 s; raise with the `LEGALPRIVACY_LOADTEST_*` environment variables). To load-test from several of your own machines, run the app on each and point them at the same target.

- **Scraped files are easy to get to.** Tools → Scrape has an "Open folder" button (opens the last job's folder in your file manager) and lists the newest files it saved.

- **Scraping through a proxy works, and says why when it can't.** A proxy is re-tested right before a job uses it (free proxies die within hours), one that fails during the job is dropped and the next tested one is tried (up to 5), and if none is left the job stops rather than carrying on without a proxy (which would show your own address). Errors now name the real cause (for example "the proxy refused or dropped the connection (Tunnel connection failed: 403 Forbidden)") instead of a line cut off after "Caused by S".

- **After an update the app asks: keep your settings, or start from the new defaults?** Asked once, in the window and on the dashboard. Starting fresh saves your old settings as a backup file (`config.before-<version>-<time>.yaml`) and keeps your traffic history, My List, sign-ins, saved bridge lines and the relay's identity. Until you answer, the noise, Tor and the relay wait; with no answer for 3 minutes (for example no window open) the settings are kept and everything starts as usual.
- **Fixed: switching duck.ai chat noise off did not survive a restart.** A one-time settings migration ran on every launch and switched it back on.

- **Whonix and Qubes-Whonix are detected, and the gateway's Tor is used.** On a Whonix-Workstation (VirtualBox/KVM or Qubes), or a Qubes qube whose network qube is sys-whonix, the app attaches to the Whonix-Gateway's Tor (SOCKS 9050, control port 9051 through onion-grater) instead of installing and starting its own, which would be Tor over Tor. Detection uses Whonix's own marker files and, on Qubes, `qubesdb-read /qubes-gateway`. The relay is not offered there (it could not be reached), and the log says how to keep your relays to avoid on the gateway (`/usr/local/etc/torrc.d/50_user.conf`), since the gateway's Tor picks the relays. On by default; "On Whonix / Qubes-Whonix, use the gateway's Tor" on the Tor tab switches it off. The Details card shows the gateway as the mode.

- **Tor connects with the US on the avoid list, bridges included.** With any country in the avoid list, Tor's default also refused every address it cannot place in a country, which is the placeholder address Snowflake and meek bridges use: they were refused at once ("Not using bridge at [scrubbed]: it is in ExcludeNodes") and Tor sat there. Tor is now told to let unknown addresses through (`GeoIPExcludeUnknown 0`), and the running relays with no known country are excluded one by one instead (from Tor's public relay list), so the avoid list is exactly as strict as before. (This is documented Tor behaviour since 2013, ticket #7706: `GeoIPExcludeUnknown auto` adds `{??}` whenever a country is excluded.) Bridges the avoid list rules out (for example the built-in obfs4 bridges in the US) are left out of Tor's configuration, so Tor never waits on them. The avoid list still applies to every hop, bridges included, and the app never loosens it.
- **No more Tor log flood.** Tor repeats "Not using bridge at [scrubbed]: it is in ExcludeNodes" every second for as long as an avoided bridge is configured, even after it has connected through another one. Avoided bridges are no longer given to Tor, and if the line appears anyway it is shown once per start with an explanation.
- **Tor gets itself unstuck.** If Tor makes no progress for 90 seconds, exits, or has every bridge refused, the app tries the next way to connect: what you chose, then direct, then the built-in obfs4, Snowflake and meek bridges, then your saved bridges (a way whose bridges are all ruled out is skipped). After the last one it resets Tor completely (deletes Tor's saved state: guards and cached relay lists) and starts again, waiting longer each round (up to 10 minutes). It only stops when you stop Tor.
- **"Get bridges that work here" works.** The bridge service answers "no bridges needed" for countries it sees no blocking in (the US among them), and the app showed that as "no bridges for that country" without naming the country. It now says which country the service saw, uses the service's default bridges in that case (as Tor Browser does), and leaves out bridges your avoid list rules out, saying how many.
- **The Tor tab's Details card shows the bridge in use**: none (direct), or the bridge type, the bridge Tor is connected through (address and country when it has a real one, its fingerprint) and whether it was chosen automatically.
- **CI**: jobs have time limits (tests 20 minutes, a healthy run takes about 6), and the leftover-Tor test no longer depends on how the runner's `sleep` is built.

- **An update no longer fails on a leftover process.** Reported: an update installed but the new version then could not start because of a conflicting process. Likely causes, all addressed (I could not reproduce the exact failure here): (1) a Tor or relay Tor from the old run still held the data folder and ports; (2) after an update restart the leftover relay Tor's parent is the restarted program itself (the process id is kept), which the relay check mistook for "another window" and refused; (3) a downloaded single-file program restarting itself reuses the old copy's unpacking folder unless told to start fresh. Now: before restarting, the app stops Tor and the relay, then stops any Tor still left; **every time Tor or the relay starts, any Tor left by an earlier run is stopped first**; the restart tells the new program to unpack afresh (`PYINSTALLER_RESET_ENVIRONMENT=1`); and if the restart itself fails, the old version keeps running (or, under systemd, exits so the service starts the new file). Only Tor programs whose command line names this app's own Tor folders and that no other running legalPrivacy window owns are stopped: your own system Tor and Tor Browser are never touched, and no sudo is needed (same user). Tested with stand-in processes.

- **The "Tor DNS" option is relabelled, moved to the very bottom of the Tor tab and collapsed.** It is now "Advanced, not recommended: use Tor to look up ordinary website names for other programs", and says plainly what it is: it makes Tor's local DNS port answer lookups of ordinary (clearnet) names such as example.com, resolved by Tor exit relays, for other programs on this computer. It has nothing to do with .onion addresses (those need no DNS lookup and are always handled inside Tor, whatever it is set to), and the noise never uses it. Still off by default; no behaviour changed. Its "share with other devices on my network" sub-option (off, one private address you pick) is unchanged; say if you want it removed.

## v2.22.0

- **Practice mode is gone; Tor's "strict" exclusion is permanent; the Tor log has a Clear button.** (1) **Practice mode is removed** (option, code, saved setting and docs): the relay is always a public middle relay (or a bridge if you pick that), never an exit. It was the source of Tor's warning *"The IPv4 ORPort address 127.0.0.1 does not match the descriptor address ..."*: a loopback-only ORPort that Tor then tried to describe with your real address. A saved practice-mode relay now loads as the public middle relay, on. The relay checklist still has to be ticked to start it (ticked for you). (2) **Strict is always on and no longer an option**: the relays and countries Tor must avoid (the `{us}` default, your list, the banned relay and the Virginia/government ranges) are written as `ExcludeNodes` with `StrictNodes 1` every time, even when that means Tor cannot connect. The checkbox and the setting are gone. (3) **The Tor log (Tor tab) has a Clear button** that empties the box so you see only the lines that come next (web and desktop); the Live Log tab already had one.

- **Stays away from Virginia and government addresses (Settings, on by default).** Never used: IPv4 addresses in the US Department of Defense /8 blocks that IANA's registry lists (6, 11, 22, 26, 28, 29, 30, 33, 55, 214, 215) and addresses that DB-IP's free City Lite database places in Virginia (about 120,000 ranges, downloaded once a month into the app folder). Applied to: Tor (the government blocks and every running relay found in those ranges, from Tor's public relay list refreshed daily, go into `ExcludeNodes`; the relay list takes effect the next time Tor starts), noise visits (a site whose address, looked up the normal way and remembered for an hour, is in those ranges is skipped for another), free proxies (dropped when tested) and Spray's resolvers. Honest limits: geolocation is a best guess (CDN and cloud addresses can be pinned to a city they are not in), so it is broad rather than exact, and about 14% of popular sites have some address in Virginia (ad networks, Amazon hosting), which is why the visit check picks another site rather than stopping; it cannot reach what a web page loads on its own (ads, fonts), IPv6, or the app's own update checks. Virginia data: IP Geolocation by DB-IP (db-ip.com), CC BY 4.0.

## v2.20.0

- **DNS helper for other Tor users, and maximum DNS security.** (1) New relay mode **DNS helper** (Tor tab, and `legalprivacy relay gen --dns`): an exit relay that does **only DNS**. Tor answers other people's name lookups from it, and its exit policy lets out nothing except port 53 of two Quad9 addresses (checked with a real `tor --verify-config`), so it cannot be used to reach websites; the resolver is hardened (random letter case, hijack detection, no search domains). Honest limits: Tor gives no Exit label to a relay that allows no web ports, so far fewer clients will pick it than a normal exit (it helps, modestly); it answers strangers' lookups, which can draw questions to your internet provider; it must be reachable from the internet (a forwarded port). So it starts in **practice mode** (loopback only, nothing published) and going public asks you to confirm; nothing here makes your computer a public relay without that step. Middle relays and bridges are unchanged and still exit nothing; a general exit is still refused. Not tried on the live Tor network. (2) **DNS lookups are encrypted by default**: the default mode is now "secure resolvers only", and those lookups go over TLS (DNS over TLS, port 853, certificate checked against the resolver's name, never a plain-text retry); a resolver that cannot do TLS is swapped for Quad9 or Cloudflare (both validate DNSSEC). Settings > DNS lookups has a switch, and "Your normal DNS" and "Mix" are still there (they blend in with your own lookups, which encrypted noise does not: choose by what you want an observer to see). (3) **Onions and Tor**: the name is always looked up by Tor (socks5h), and the Tor client now also refuses answers that point inside your network. Tested with stand-ins (framing, certificate name, no plain fallback); the real exchange with Quad9 or Cloudflare is untested, because my sandbox refuses connections to port 853 (checked: connection refused).
- **Nothing stops the noise but you.** Repeated failures only change behaviour (slower pacing, a new identity, fresh Tor circuits, a Tor restart, other sites); the only automatic pause left is a daily data limit that you set yourself, which ends at midnight.
- **Tor downloads, and sessions and identities capped at two hours.** (1) The Tor lane now carries some of the file downloads too (the same real public files, up to 12 MB over Tor, never an upload), picked at random alongside the clearnet ones (about 40% of the file transfers go over Tor when Tor is on) while the onion browsing carries on at the same time, so Tor use looks like browsing plus the odd file fetch. It follows "File transfers" in Settings. (2) **No identity lives longer than two hours**: each one gets a random lifetime of 35 minutes to 2 hours, then it is replaced (a new browser fingerprint, and on Tor a new circuit). (3) **Long sessions** (a page you keep coming back to, or leave open and return to) are capped at two hours in total, including a stretch away followed by coming back; when one ends, or its identity expires, the next visit is as a new identity. (4) Long sessions no longer take over: they always run alongside the shorter ones (the old "mostly on it alone" mode is gone). Tested with a fake clock; not watched live over days.
- **DuckDuckGo is the main search engine by default.** The default mix is now about 70% DuckDuckGo (plus 2.5% its lite page), 12% Google, 4% each Bing and Brave, 3% Startpage and a trace of Ecosia, Mojeek and Qwant (it was a 35/35 split with Google). It applies to every profile that has not set its own weights in Settings > Search engines (which still wins); the old special case for one persona is gone because the default is now the same.

## v2.19.0

- **Fix (remote runner): the headless-browser lane now applies the same public-addresses-only rule as the plain HTTP lane**: a link found on a search page that pointed at a private, loopback or link-local address could previously have been opened by the browser. Checked on a real Chromium as an unprivileged user (the browser lane works; Chromium refuses to start as root, in which case the runner falls back to plain HTTP) and on a live HTTPS fetch.
- **Remote machines: run the noise on other computers you own, over SSH** (new Remote tab in the web dashboard and the desktop app, with the same features: add, test connection, trust a host key, start, stop, remove, status and a log for each machine). Give `user@host[:port]` and either a password or a private-key path (and passphrase). The app copies ONE stdlib-only runner (`remoteagent.py`, plus a settings file) into `~/.cache/legalprivacy` (Windows: `%LOCALAPPDATA%\\legalprivacy`) in that account, starts it over SSH and streams its log back; Stop ends it, Remove also deletes the folder. No root, no service, no display: a headless Linux machine works (a headless Chromium/Chrome/Firefox is used when one is installed, otherwise plain HTTP). It needs Python 3 on the machine.
